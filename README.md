# Failoverly

Статический сайт для **https://failoverly.app** на HTML, CSS и небольших ES-модулях. Лендинг редактируется в `index.html`, отдельная политика приватности — в `privacy.html`.

## Разработка

Нужен Bun 1.3.11 или новее.

```sh
bun install --frozen-lockfile
bun run dev
```

Сайт откроется на `http://localhost:8000`. CSS и HTML/JS обновляются при изменении исходников; отдельный препроцессор не нужен.

| Что менять                                              | Файл                               |
| ------------------------------------------------------- | ---------------------------------- |
| Тексты, семантическая разметка, логотип, метаданные     | `index.html`                       |
| Краткая политика приватности сайта от бренда            | `privacy.html`                     |
| Цвета, размеры, отступы и адаптивная flexbox-вёрстка    | `css/main.css`                     |
| CSS из HTML-вставки Kit                                 | `css/kit-form.css`                 |
| Переключение диаграммы                                  | `scripts/connection-preview.js`    |
| Синхронизация сообщений об успехе форм Kit              | `scripts/signup-forms.js`          |
| Основной домен, публичный Meta Pixel ID и дата контента | `site.config.json`                 |
| Доступ краулеров и ссылка на sitemap                    | `robots.txt`                       |
| Краткое описание продукта для AI-инструментов           | `llms.txt`                         |
| Генерация иконок и изображения для соцсетей             | `tooling/brand-assets.mjs`         |
| Сборка и конфигурация размещения                        | `tooling/build.mjs`, `vercel.json` |
| Политика безопасности контента (CSP)                    | `tooling/security.mjs`             |

`css/main.css` — редактируемый исходник, который хранится в Git. Минифицированный CSS создаётся только внутри production-сборки. `bun run format` форматирует исходники; `bun run format:check` проверяет форматирование.

Масштаб основного текста и подписей контролов задаётся через `--type-scale` в `css/main.css` (сейчас `1.1`, то есть +10%). Заголовки и подзаголовки сохраняют собственные размеры. Цвета находятся в `:root`; границы полей и кнопки диаграммы используют `--control-border` с контрастом выше 3:1 на обоих фонах. Для системных шрифтов используются веса 400/600/700.

## Production-сборка

```sh
bun run build
bun run preview
```

Готовый сайт находится в `dist/`, локальный предпросмотр — `http://127.0.0.1:4173/`.

- Локальные CSS и JS минифицируются и встраиваются в HTML. JS сайта остаётся модулем (`type="module"`), который выполняется после разбора HTML. Исходники CSS и ES-модулей остаются читаемыми и раздельными. Разметка обеих форм и CSS Kit входят в страницу; общий обработчик Kit загружается один раз с `defer`.
- Подпись логотипа превращается в SVG-контуры из локального Inter при сборке: браузеру не требуется загружать шрифт. Основной текст использует системный стек. SVG, иконки и social card включены в сборку. Дополнительно загружаются ресурсы встроенных форм Kit и Vercel Web Analytics; Meta Pixel загружается только после разрешения рекламного трекинга.
- В HTML сохранены весь контент и FAQ: JavaScript используется для диаграммы, форм, аналитики и выбора рекламного трекинга.
- Сборка создаёт `sitemap.xml`, переносит `robots.txt`, `llms.txt` и лицензию шрифта.
- В `dist/` попадают только готовые HTML-страницы, используемые assets, лицензия шрифта и файлы для краулеров.
- Для Vercel одновременно создаётся `.vercel/output/` в формате Build Output API v3: копия сайта в `static/` и `config.json` с маршрутами и HTTP-заголовками, включая CSP. Оба каталога сборки игнорируются Git.

Домен задаётся в `site.config.json`. При необходимости его можно переопределить переменной `SITE_URL`, например `SITE_URL=https://example.com bun run build`. Она должна содержать HTTPS origin без пути. Сборка обновляет canonical, Open Graph, JSON-LD, sitemap, robots и ссылки в `llms.txt`. Пример локальной конфигурации — `.env.example`; для домена `failoverly.app` ничего переопределять не нужно.

Каждая production-сборка обновляет брендовые assets из логотипа в `index.html`. Перегенерировать их отдельно можно командой:

```sh
bun run assets
```

## SEO и AI-краулеры

`robots.txt` разрешает всем краулерам читать страницу и её assets, содержит абсолютный URL sitemap. Отдельные повторяющиеся правила для Googlebot, Bingbot, OAI-SearchBot и других ботов не нужны. Это разрешение на обход, а не гарантия индексации: доступ также зависит от настроек Vercel/CDN. См. [правила Google для robots.txt](https://developers.google.com/crawling/docs/robots-txt/create-robots-txt).

`llms.txt` следует [предложенному формату llms.txt](https://llmstxt.org/): краткое определение, проверяемые факты, ограничения и ссылки на доступные разделы сайта. Он не заменяет HTML, sitemap или structured data и не гарантирует цитирование. [Google не требует специальных AI-файлов](https://developers.google.com/search/docs/appearance/ai-features); основной контент и FAQ доступны в HTML без JavaScript.

Sitemap включает только индексируемый лендинг. Служебная страница `privacy.html` доступна по ссылкам, но помечена `noindex, follow` и исключена из sitemap. Это не ограничивает чтение политики посетителями или рекламными платформами. Несуществующие страницы в sitemap не добавляются. При смене цены, требований или статуса запуска обновляйте `index.html` и `llms.txt` вместе.

`lastmod` берётся из `contentLastModified` в `site.config.json`. **TODO при изменении контента:** обновляйте эту дату при существенных правках текста, ссылок или structured data. Повторная сборка, правка CSS или конфигурации CI не должны менять дату. Сборка проверяет формат `YYYY-MM-DD` и запрещает будущие даты.

Приложение описано как prelaunch без предложения купить или оформить предзаказ. **TODO после появления реального предложения:** добавить `offers` с ценой подписки и месячным периодом, отражающими видимые условия страницы. Для расширенного результата Google также нужен реальный отзыв или рейтинг; лист ожидания не является `PreOrder`.

## Vercel

Подключите GitHub-репозиторий к проекту Vercel и выберите `main` как Production Branch. После этого push или merge в `main` запускает production-деплой; изменения в других ветках и pull request создают Preview согласно настройкам проекта. Теги для публикации не нужны. Статус и URL сборки доступны в Vercel и GitHub. См. [нативную интеграцию Vercel с GitHub](https://vercel.com/docs/git/vercel-for-github).

Настройки сборки уже находятся в `vercel.json`:

- Framework Preset: **Other**.
- Install Command: `bun install --frozen-lockfile`.
- Build Command: `bun run build && bun tooling/check-build.mjs`.
- Output Directory: `dist`; Vercel использует выпускаемый сборкой `.vercel/output/` в формате [Build Output API](https://vercel.com/docs/build-output-api).

Фактические маршруты и заголовки находятся в `.vercel/output/config.json`. Настройки `headers` из исходного `vercel.json` переносятся туда сборщиком. CSP добавляется после минификации; вручную прописывать меняющиеся хеши в `vercel.json` не нужно. Ошибка сборки или проверки сайта останавливает публикацию.

В Domains проекта добавьте `failoverly.app` и примените DNS-записи, которые покажет Vercel. GitHub Actions secrets, Variables и environment `production` для нативной интеграции не требуются. Публичный `SITE_URL` уже задан в `site.config.json`; при необходимости переопределите его в Vercel → Environment Variables для нужного окружения. Секреты для сборки страницы и runtime-переменные для формы Kit не нужны. Перед запуском waitlist завершите настройки Kit и сквозную проверку регистрации, описанные ниже.

### Ручная публикация через CLI

В корне репозитория один раз войдите в Vercel и привяжите папку к существующему проекту:

```sh
bunx vercel@59.17.0 login
bunx vercel@59.17.0 link
```

При `link` выберите тот же проект, который подключён к GitHub. Локальная привязка хранится в `.vercel/project.json` и не коммитится. Версия CLI `59.17.0` проверена с настроенным в Bun `minimumReleaseAge = 604800` (7 дней); при обновлении учитывайте возраст релиза.

Перед публикацией проверьте сайт:

```sh
bun run check
```

Для Preview уже созданного проекта после первого деплоя:

```sh
bunx vercel@59.17.0
```

Для Production:

```sh
bunx vercel@59.17.0 --prod
```

Обе команды отправляют исходники из текущей локальной папки, включая незакоммиченные изменения, и выполняют сборку на Vercel по `vercel.json`. У нового проекта самый первый деплой становится Production даже без `--prod`; поэтому для Preview сначала завершите первоначальный импорт и деплой через GitHub. Подробнее — [Vercel CLI deploy](https://vercel.com/docs/cli/deploy).

Production разрешает индексацию. Сборки с `VERCEL_ENV=preview` получают `noindex, nofollow`; robots остаётся открытым, чтобы краулер мог прочитать этот запрет. Кеширование хешированных assets и основные HTTP-заголовки заданы в `vercel.json` и переносятся в Build Output API. Отсутствующие страницы возвращают 404; `/index` и `/index.html` перенаправляются на `/`.

После первой публикации проверьте `https://failoverly.app/robots.txt`, `/sitemap.xml`, `/llms.txt` и добавьте sitemap в Google Search Console / Bing Webmaster Tools. Подтверждение домена через DNS не требует менять код страницы.

Подключён `@vercel/analytics` для базовой статистики просмотров лендинга и политики приватности: страницы, источники переходов, страны, устройства и браузеры. Локальный инициализатор минифицируется и встраивается в HTML, затем загружает `/_vercel/insights/script.js` с `defer`. Vercel Web Analytics не использует аналитические cookies; подробнее — [описание приватности Vercel](https://vercel.com/docs/analytics/privacy-policy).

## Meta Pixel

Публичный Pixel/Dataset ID `1112673731737820` задан строкой в `site.config.json` → `metaPixelId`. Это браузерная интеграция: API token, серверный endpoint, GTM и секретные переменные не нужны. Pixel работает только по HTTPS на основном домене из canonical и его варианте с `www` — сейчас это `failoverly.app` и `www.failoverly.app`. Vercel Preview/Development и localhost исключены; `SITE_URL` меняет основной домен и это ограничение вместе с ним. Интерфейс выбора можно проверять локально, но он не должен отправлять события Meta.

До явного **Allow** сайт не загружает скрипты и не делает сетевых запросов Meta. **Reject** оставляет сайт и формы доступными. Выбор сохраняется в `localStorage` под ключом `failoverly.adConsent.v1` и действует 180 дней; **Cookie settings** в футере лендинга и политики позволяет открыть выбор снова. При отзыве согласия прекращается трекинг на текущей странице и удаляются доступные сайту first-party cookies `_fbp`/`_fbc`. Это не удаляет уже отправленные данные или cookies на доменах Meta. При `navigator.globalPrivacyControl === true` Meta остаётся выключенным. Согласие на рекламный трекинг отдельно от подписки на анонс.

После Allow отправляется `PageView`. Событие `Lead` отправляется только после успешного принятия формы Kit, при действующем согласии; клик, ошибка формы и подтверждение email не являются этим событием. `Lead` **не означает завершённый double opt-in**. Сайт не добавляет email или значения полей формы в события и не включает advanced matching. При этом Pixel получает URL, referrer, IP, сведения о браузере/устройстве и cookie-идентификаторы; это не режим без персональных данных. Не передавайте email и другие персональные данные в URL или UTM. Использование данных Meta описано в [Meta Privacy Policy](https://www.facebook.com/privacy/policy/).

## Content Security Policy

`tooling/security.mjs` формирует отдельную CSP для каждого документа. Локальные inline-скрипты получают SHA-256-хеши после минификации; обе страницы разрешают скрипт и запросы Vercel Web Analytics со своего origin и необходимые источники Meta Pixel. Разрешение источника в CSP само по себе не запускает Pixel: загрузку контролирует согласие. Для лендинга дополнительно разрешены необходимые ресурсы, стили и запросы нативной формы Kit. Kit добавляет `<style>` и style-атрибуты во время загрузки, поэтому только лендинг разрешает `unsafe-inline` для CSS; разрешение не распространяется на JavaScript. В `privacy.html` работают аналитика и выбор рекламного трекинга; содержание политики доступно без JavaScript, хеши CSS сохранены. Политика передаётся HTTP-заголовком; локальный `bun run preview` читает те же заголовки из `.vercel/output/config.json` и подхватывает изменения после пересборки.

Единственный внешний скрипт Kit — `https://f.convertkit.com/ckjs/ck.5.js`: он загружается с `defer` и `crossorigin="anonymous"`, без cross-origin credentials. Разметка форм хранится в `index.html`; загрузчик `https://failoverly-app.kit.com/eba19436d6/index.js` больше не запрашивается и не разрешён CSP. Kit учитывает посещения через `app.convertkit.com` и отправляет заявки в `app.kit.com`. Разрешения Kit ограничены лендингом; произвольные сторонние скрипты, `eval`, обработчики в HTML-атрибутах, встраивание сайта во фрейм и плагины не разрешены. При обновлении HTML-вставки Kit повторно проверьте её ресурсы и CSP. Dev-сервер на порту 8000 использует Bun HMR; production-политику проверяйте через `bun run preview`.

## Формы Kit и Privacy Policy

В первом экране и внизу страницы встроена одна и та же нативная форма Kit: UID `eba19436d6`, ID `9949657`. Источник разметки и настроек — предоставленный HTML-код формы Kit; обе копии находятся в `index.html`. CSS провайдера вынесен в `css/kit-form.css` и подключён перед `css/main.css`. Поля и связанные с ними подписи доступны сразу, без ожидания внешнего скрипта. Общий обработчик `https://f.convertkit.com/ckjs/ck.5.js` управляет отправкой, ошибками и сообщением об успехе обеих форм. Этот ресурс поддерживает загрузку с `crossorigin="anonymous"`.

Изменения формы в кабинете Kit не обновляют локальную HTML-вставку автоматически. При изменении формы заново перенесите её HTML, настройки и CSS, сохраняя уникальные ID полей, связи с подписями и текстом о приватности, а также настройки брендинга из актуального кода Kit. В текущей вставке брендинг отключён (`powered_by.show: false`), поэтому подписи «Built with Kit» нет. Собственного signup API у сайта нет. Серверный runtime и секретные API-ключи не нужны; публичный UID не является секретом.

При успешной отправке `scripts/signup-forms.js` показывает исходное сообщение Kit в обоих местах: это одна форма с одинаковым UID, и обработчик Kit может обновить только одну её копию. Сообщение просит проверить почту и подтвердить подписку. Оно само по себе **не подтверждает настройку double opt-in в кабинете**. После отправки нет дополнительного опроса. Не удаляйте UTM-параметры из URL при загрузке: нативная форма использует их для атрибуции. Не передавайте email или другие персональные данные в UTM и URL.

## Проверки

```sh
bun run check
bun run check:pixel
bun run audit
bun run audit:3g
```

`check` проверяет форматирование и production-сборку, включая локальные assets, отсутствие дубликатов, метаданные, правила robots, sitemap, ссылки из `llms.txt` и режим индексации. Он сверяет CSP-хеши с финальным HTML и проверяет соответствие файлов для Vercel локальному предпросмотру. Та же проверка сборки выполняется в Build Command на Vercel перед публикацией. `audit` пересобирает сайт, запускает локальный сервер и проверяет его в Chrome Lighthouse с обычными мобильным и десктопным профилями. Нужны Google Chrome и Node.js 22.19+; при нестандартном пути к Chrome задайте `CHROME_PATH`.

`check:pixel` проверяет уже собранный сайт в Chrome, используя настоящие публичные скрипты Kit и Meta. Все события Meta перехватываются, ответы на заявки Kit подставляются: проверка не создаёт подписчиков и не отправляет рекламные события. Нужны Node.js и Google Chrome (`CHROME_PATH` поддерживается). Проверяются согласие, отказ, отзыв во время загрузки, GPC, ошибки формы, обе формы и исключение локальных/preview-адресов. Отчёт и снимки панели сохраняются в `reports/meta-pixel-check.json` и `reports/meta-consent-*.png`. Проверка не подтверждает получение событий в Events Manager.

HTML/JSON-отчёты сохраняются в `reports/`; краткий результат — `reports/summary.json`. Команда завершится ошибкой, если хотя бы одна из четырёх категорий ниже 100. Отчёты не коммитятся.

`audit:3g` отдельно проверяет холодную загрузку с реальным ограничением DevTools: **400 Кбит/с в обе стороны, 2000 мс задержки**, CPU ×4 на mobile и ×1 на desktop. Сетевые значения соответствуют [профилю Slow 3G в Chromium](https://chromium.googlesource.com/devtools/devtools-frontend/+/HEAD/front_end/core/sdk/NetworkManager.ts). Отчёты: `reports/lighthouse-mobile-slow-3g.report.html`, `reports/lighthouse-desktop-slow-3g.report.html` и `reports/summary-slow-3g.json`. В summary записаны параметры, FCP, LCP, Speed Index, TBT и CLS. Этот стресс-профиль сохраняет реальные оценки и не требует 100: сама двухсекундная задержка сети влияет на метрики даже без блокирующих ресурсов. Сравнивайте результаты только при одинаковых настройках.

Локальная проверка production-сборки от **2026-09-23** с HTML-вставкой Kit, **с интерфейсом выбора трекинга, до согласия на Meta** (Lighthouse 13.4.1, Chrome 154):

| Профиль         | Performance | Accessibility | Best Practices | SEO | LCP    |
| --------------- | ----------- | ------------- | -------------- | --- | ------ |
| Обычный mobile  | 100         | 100           | 100            | 100 | 0,81 с |
| Обычный desktop | 100         | 100           | 100            | 100 | 0,21 с |
| Slow 3G mobile  | 95          | 100           | 100            | 100 | 2,44 с |
| Slow 3G desktop | 72          | 100           | 100            | 100 | 2,45 с |

Meta не загружается до согласия, а на локальном адресе отправка рекламных событий отключена. Эти оценки не характеризуют загрузку с уже разрешённым Pixel. `check:pixel` отдельно проверил 11 сценариев с реальным SDK: только `PageView` и `Lead`, без email в событиях, без ошибок JavaScript и нарушений CSP. Все заявки и рекламные события в этой проверке перехвачены.

Профиль Slow 3G использует указанные выше 400 Кбит/с и 2000 мс задержки. Это результаты локального предпросмотра, а не опубликованного сайта; после публикации повторите аудит по настоящему HTTPS-адресу.

При прежней JavaScript-вставке от 2026-09-22 Best Practices составлял 77 из-за защитной cookie загрузчика Kit. Теперь этот загрузчик удалён, а общий обработчик `f.convertkit.com/ckjs/ck.5.js` загружается с `crossorigin="anonymous"`. Проблема с повторяющимися CORS-заголовками прежнего загрузчика не относится к текущему обработчику.

В локальном браузере проверены адаптивная вёрстка на desktop и mobile, отсутствие нарушений CSP и ошибок JavaScript, отправки с подставленными ответами об ошибке и успехе, повторная попытка после ошибки. При отправке из каждого размещения сообщение об успехе появлялось в обоих местах, а поля email скрывались. Запросы формы сохраняли `host`, `search` и UTM. Браузер не сохранил cookies, хотя ответ обработчика Kit содержал `Set-Cookie`; это наблюдение относится к проверенному сценарию и не исключает cookies у размещённой в Kit формы или при дополнительных защитных проверках. Реальная подписка не выполнялась: доставка писем, double opt-in и атрибуция в кабинете Kit требуют отдельной сквозной проверки.
